# V2 → V3 晋级路线

> 状态：已采纳的实施路线 · 基线日期：2026-08-11 · 当前阶段：V3.0 已完成，下一阶段为 V3.1 / V3.2

## 1. 文档目的

本文把 [PRD](../PRD.md) 中一次性描述的 V3 能力拆成可独立实现、验证和发布的阶段。后续实现默认按照本文顺序推进；如果范围、顺序或领域语义发生变化，必须先更新本文及相关领域文档，再修改代码。

本文只细化交付路线，不取代其他基线：

- [CONTEXT.md](../CONTEXT.md) 定义领域语言；
- [PRD.md](../PRD.md) 定义产品范围和最终完成标准；
- 已接受的 [ADR](./adr) 记录难以逆转的架构决定；
- 本文定义版本切分、依赖关系、阶段边界和验收门。

本文中的 `V2.1`、`V3.0` 至 `V3.4` 是产品能力里程碑，不要求与部署使用的 Git 发布标签一一对应。

## 2. 最终目标

完成本路线后，系统应具备以下能力：

1. 用户可以主动创建 Concept，并把多个知识点纳入 Concept；
2. AI 可以基于多个生效知识点提出 Concept Candidate，但不能自动创建正式 Concept；
3. 用户可以确认、修改或拒绝候选，所有决定均保留来源和历史；
4. Concept、知识点归属、知识点关系和 Concept 关系可以组成可查询的知识网络；
5. 用户可以查看真实图谱、选中节点、回到来源并探索可解释路径；
6. 所有新增领域事实都能完整导出和恢复，并从格式 4 起向后兼容已经发布的备份；
7. V1/V2 已有记录、历史版本、知识点、证据、标签和治理决定不被批量改写。

## 3. 全路线固定原则

### 3.1 人工确认边界

- AI 输出只能形成 Candidate 或 Suggestion；
- 只有用户明确确认后才能形成 Concept 或正式关系；
- Mode A 不适用于 Concept 和知识关系；
- 相似度、聚类结果和模型置信度都不能直接进入正式知识网络。

### 3.2 版本与溯源

- Concept Membership 初期绑定一个确切、不可变的 Knowledge Point；
- 重新整理产生新的 Knowledge Point 身份时，不自动迁移归属；
- 原端点不再生效、被排除或内容变化时，归属和关系保留历史并显示需要复核；
- 自动跨版本身份映射不属于本路线的核心范围。

### 3.3 增量数据模型

- V3 只新增结构，不批量改写 V1/V2 领域行；
- 现有 `knowledge_relations` 继续表达 Knowledge Point → Knowledge Point；
- Concept、Concept Membership 和 Concept Relation 使用独立结构；
- 知识网络通过只读聚合模型联合现有关系与新增结构，不先改造成通用多态边表；
- PostgreSQL 仍是唯一事实存储，在出现经过测量的性能瓶颈前不引入图数据库。

### 3.4 可移植性不延期

- 每个新增持久化领域对象必须在同一里程碑进入完整导出与恢复；
- 格式 4 是首个恢复兼容基线；每次格式升级都必须继续接受格式 4 及之后已经发布的格式；
- 格式 1–3 没有形成用户持有的历史备份，不纳入恢复兼容范围；
- 导出恢复、引用校验和迁移测试不是最后统一补做的收尾项。

### 3.5 先语义、后图形

- 先建立可测试的 Concept 和网络语义，再开发图谱；
- 先交付功能完整的 2D 图谱，再升级 3D 体验；
- 图谱只显示真实领域关系，装饰线不得伪装成知识边；
- 3D 渲染失败不能阻断 Concept、路径查询和来源核验。

## 4. 路线总览

| 里程碑 | 核心结果 | 相对规模 | 依赖 |
| --- | --- | --- | --- |
| V2.1 V2 收尾 | 验收 V2 完成标准，冻结导出兼容基线 | 小 | 当前 V2 |
| V3.0 Concept 核心 | 用户可以手动创建和维护 Concept 与归属 | 中 | V2.1 |
| V3.1 Concept Candidate | AI 候选和人工审查形成闭环 | 中高 | V3.0 |
| V3.2 知识网络语义 | 可查询节点、边、邻居和路径 | 高 | V3.0；可与 V3.1 部分并行 |
| V3.3 功能性图谱 | 独立 2D 知识网络工作台 | 高 | V3.1、V3.2 |
| V3.4 3D 体验升级 | 将真实网络接入一个既有主舞台 | 高、可延期 | V3.3 |

顺序如下：

```text
V2.1 → V3.0 → ┬→ V3.1 ─┐
               └→ V3.2 ─┴→ V3.3 → V3.4
```

V3.1 与 V3.2 只有在 V3.0 的数据库结构、API 合同和领域测试稳定后才可以并行。

## 5. V2.1：V2 收尾

### 5.1 目标

逐项验收 V2 完成标准，让 V2 成为能够安全承接后续格式升级和新增领域对象的稳定基线。本阶段没有 V3 用户功能。

### 5.2 交付范围

- 对照 PRD 16.2 审计标签治理、重复建议、关系建议与确认、覆盖分析和 V1 数据保持行为；
- 验证 V2 数据库迁移只新增结构，不批量改写 V1 领域行；
- 验证当前完整导出格式 4 包含全部 V2 领域事实，并能事务性恢复到空实例；
- 把格式 4 固定为首个恢复兼容基线，不为未形成用户备份的格式 1–3 增加适配器；
- 通过类型检查、领域与集成测试、端到端测试和双主题视觉回归。

### 5.3 导出兼容边界

- 恢复器只接受当前受支持格式，并继续执行严格结构、引用和空实例校验；
- 格式 4 以前的开发期格式不构成公开兼容承诺；
- 一旦后续格式正式发布，恢复器必须继续支持格式 4 及之后已经发布的格式；
- 当前导出格式升级时必须同步增加固定恢复样本和往返测试。

### 5.4 预期改动面

- 现有 `src/data-transfer-routes.ts` 已严格支持格式 4，无需修改生产代码；
- 复用现有迁移、V2 导出恢复、领域、集成、E2E 和视觉测试；
- 更新 PRD、路线文档和导出兼容 ADR；
- 不新增前端入口，不新增 Concept 表。

### 5.5 验收门

- [x] 当前格式 4 的有效备份能够事务性恢复到空实例；
- [x] 缺字段、额外字段、错误引用和损坏 ZIP 继续严格失败；
- [x] 全部 V2 领域事实经过当前格式导出恢复后不丢失；
- [x] V2 完成标准逐项有自动测试或明确验收证据；
- [x] 类型检查、Vitest、API/E2E 和双主题视觉测试通过。

## 6. V3.0：Concept 核心

### 6.1 目标

不依赖 AI 和图谱，让用户先能够建立、阅读和维护正式 Concept，验证最核心的长期聚合模型是否成立。

### 6.2 实施前领域决策门

以下问题已经在数据库迁移前确定，并由 PRD、CONTEXT 与 ADR-0031 固定：

- [x] Concept 名称和自足描述均为必填；名称使用 NFKC、Unicode 空白归一和拉丁字母大小写无关规则，在独立于 Tag 的 Concept 命名空间内唯一；
- [x] 名称与描述修改产生不可变 Concept Revision，Concept 稳定身份不变；
- [x] Concept 只支持可恢复归档，V3.0 不提供永久删除；
- [x] Membership 保持同一身份并记录加入、移除和恢复；端点失效后保留原引用、标记复核且不自动迁移；
- [x] V3.0 不新增 Concept Relation 或关系类型；Concept Relation 类型集合留到 V3.2 的关系决策门确定。

其余固定边界是：用户主动创建时至少聚合两个生效且未排除的知识点；后续成员不足不会自动删除或归档 Concept。

### 6.3 交付范围

- 新增 Concept 持久化结构；
- 新增 Concept Membership 持久化结构；
- 用户可以从多个当前生效且未排除的 Knowledge Point 创建 Concept；
- 用户可以修改 Concept 名称和描述；
- 用户可以增加、移除和恢复 Membership；
- 用户可以归档和恢复 Concept；
- Concept 详情展示成员知识点、实际来源记录、端点状态和归属来源；
- 新增 Concept 列表、详情和编辑 API；
- 新增独立 Concept 工作区，避免继续扩大现有 `insights-page.tsx` 单文件；
- 完整导出与恢复包含 Concept 和 Membership，并继续支持格式 4 及之后已经发布的格式。

### 6.4 固定领域行为

- Concept 不是 Tag，不进入标签词表，也不产生 Tag Assignment；
- Concept 是用户确认后的长期节点，用户手动创建即构成明确确认；
- Membership 是可撤销事实，移除不删除知识点或历史归属；
- Membership 绑定确切 Knowledge Point，不因重新整理自动改指向新知识点；
- Knowledge Point 不再生效时，历史 Membership 仍可查看，但不进入默认有效网络；
- 归档 Concept 不删除成员、来源或关系历史。

### 6.5 明确不做

- Concept Candidate；
- AI 自动发现或后台聚类；
- Concept Relation；
- 图谱和路径探索；
- Concept 别名、层级、合并；
- 自定义关系类型；
- 跨分析版本自动迁移 Membership。

### 6.6 预期改动面

- 1–2 个增量数据库迁移；
- 新 Concept 领域/API 模块及客户端 API 类型；
- 新 Concept 列表与详情页面；
- 导航增加可发现入口，但不替换首页或搜索；
- 导出恢复格式升级及格式 4 以后已发布格式的适配；
- 迁移、API、集成、E2E 和导出恢复测试。

### 6.7 验收门

- [x] 用户能够从至少两个有效知识点创建 Concept；
- [x] Concept 和 Membership 的创建、修改、撤销、归档与恢复均可追溯；
- [x] 重分析、排除知识点和归档记录不会静默改写 Membership；
- [x] Concept 永远不会混入 Tag 或 Tag Assignment；
- [x] V2 数据升级前后身份、内容和引用保持不变；
- [x] 当前格式 5 与兼容基线格式 4 均可恢复；
- [x] 核心领域、API、E2E 和恢复测试通过。

## 7. V3.1：Concept Candidate

### 7.1 目标

让 AI 提出可审查的 Concept Candidate，并通过人工确认形成正式 Concept 和 Membership。

### 7.2 交付范围

- 新增 Concept Candidate 及其输入知识点快照；
- Candidate 保存建议名称、描述、成员、生成理由、模型信息和输入内容指纹；
- 用户显式选择知识范围或主动发起扫描；
- 生成过程具有排队、运行、成功、失败和重试等可观察状态；
- 用户可以修改名称、描述和成员后确认，也可以拒绝或稍后处理；
- 确认操作在同一事务中创建 Concept、Membership 和确认记录；
- 同一输入及内容指纹已经确认或拒绝后，不重复提出等价候选；
- 输入知识点发生实质变化时，Candidate 显示过期并阻止直接确认；
- Candidate 和全部审查决定进入导出恢复。

### 7.3 初始召回边界

- 第一版只做用户主动发起，不做静默后台扫描；
- 第一版应限制输入范围并记录完整快照，不进行无界全库聚类；
- Embedding 或聚类只负责召回组合，文本模型负责给出候选内容和理由；
- 召回阈值不能直接创建 Concept，也不能替代用户确认。

具体输入上限、候选数和超时策略必须通过测试数据和模型调用预算确定，不在迁移中写死未经验证的数值。

### 7.4 明确不做

- 自动确认 Candidate；
- 自动把新分析版本加入已有 Concept；
- Concept 合并、别名或层级；
- 图谱布局；
- 无用户动作的持续后台聚类。

### 7.5 预期改动面

- Candidate、输入快照和任务生命周期迁移；
- Concept 生成器、校验器、路由和任务恢复逻辑；
- Candidate 审查工作区；
- AI 任务观察入口；
- 导出恢复及兼容测试；
- 领域、集成、E2E 和超时/重试测试。

### 7.6 验收门

- [ ] AI 只能创建 Candidate，不能直接写入 Concept；
- [ ] Candidate 的每个成员都能回到确切 Knowledge Point 和原文证据；
- [ ] 确认、修改后确认、拒绝和过期行为均有集成测试；
- [ ] 迟到任务不会基于已变化的输入发布可确认 Candidate；
- [ ] 等价的已处理输入不会反复推荐；
- [ ] 任务失败不影响已有 Concept、记录和搜索；
- [ ] Candidate 与决定可以完整导出恢复。

## 8. V3.2：知识网络语义与 API

### 8.1 目标

先建立与渲染器无关、可验证的知识网络读取模型，使节点、边、邻居和路径都拥有稳定语义。

### 8.2 网络读取模型

第一版网络包含：

- 节点：有效 Concept、当前生效且未排除的 Knowledge Point；
- 边：有效 Concept Membership；
- 边：V2 已确认且未撤销的 Knowledge Relation；
- 边：V3 已确认且未撤销的 Concept Relation。

默认网络和路径只使用当前有效且已确认的事实。历史端点、已撤销边和需要复核的边仍可在详情中查看，但不参与默认遍历。

### 8.3 交付范围

- 新增 Concept Relation 及必要的建议/确认结构；
- 保留现有 Knowledge Relation 表，不迁移成多态边；
- 提供按节点读取邻居和局部子图的 API；
- 提供有边界的路径探索 API；
- 路径返回有序节点、真实边、关系类型、方向、描述和来源；
- Concept 详情展示直接邻居和已确认关系；
- 所有网络对象和确认记录进入导出恢复；
- 为局部子图规模、最大路径深度、超时和响应体建立明确预算。

### 8.4 关系决策门

开始 Concept Relation 迁移前必须决定：

- 第一版是否只允许 AI 建议后确认，还是也允许用户直接创建；
- Concept Relation 是否完全复用 V2 六种预设类型；
- 哪些关系有方向，路径是否允许反向遍历；
- 同一对 Concept 是否允许同时存在多种有效关系；
- 端点归档、成员变化和内容变化分别如何触发复核。

无论采用哪种创建方式，AI 都不能绕过人工确认形成正式边。

### 8.5 路径语义

- 路径是现有确认事实的遍历结果，不是 AI 推理链；
- 每一步必须引用一个真实 Membership、Knowledge Relation 或 Concept Relation；
- 系统不得为了连通两个节点而生成不存在的中间关系；
- 找不到路径是有效结果，不降级为语义相似度解释；
- 第一版优先使用 PostgreSQL 查询或服务端有界遍历，不引入图数据库。

### 8.6 明确不做

- 图谱渲染；
- 自定义关系类型编辑器；
- Ontology；
- 自动修复或补全断开的路径；
- 基于图路径生成无来源的 AI 答案。

### 8.7 验收门

- [ ] 网络 API 只返回有效、已确认的默认节点和边；
- [ ] 任一节点和边都能回到来源与确认记录；
- [ ] 邻居、方向、多关系、撤销、归档和过期行为有集成测试；
- [ ] 路径结果逐边可核验，找不到路径时明确返回空结果；
- [ ] 大输入受到边界和超时保护；
- [ ] 不需要 Neo4j 等新增基础设施即可通过目标规模测试；
- [ ] 全部网络对象可以完整导出恢复。

## 9. V3.3：功能性知识图谱

### 9.1 目标

在不依赖 3D 的前提下完成真实知识网络的浏览、选中、核验和路径探索，达到 PRD 的核心 V3 完成标准。

### 9.2 交付范围

- 新增独立 `/network` 工作区；
- 初始视图以 Concept 为主要节点，Knowledge Point 按选择或局部展开加载；
- 只绘制网络 API 返回的真实边；
- 支持节点搜索、类型筛选、关系筛选、聚焦和重置视图；
- 支持选择起点和终点并高亮一条可解释路径；
- 节点选择写入 URL，刷新、浏览器返回和前进保持预期状态；
- 右侧推挤式详情抽屉支持 Concept 和 Knowledge Point；
- 打开抽屉只调整视口，不重新计算稳定布局；
- 提供键盘可操作的等价节点/关系列表；
- 遵循减少动态效果偏好，渲染失败时保留功能性列表视图。

### 9.3 布局原则

- 布局只表达真实网络结构，不使用无语义随机邻接；
- 同一网络快照在多次访问中保持稳定，不因抽屉开合重排；
- 局部扩展不得让已显示节点发生无法追踪的大幅跳动；
- 颜色不能成为区分节点类型、关系类型或状态的唯一方式；
- 装饰元素必须与真实关系边有可感知差异，默认优先不画装饰线。

### 9.4 明确不做

- 替换现有首页；
- 替换搜索结果主舞台；
- 3D 自由漫游；
- Concept 别名、层级或自定义关系类型；
- 为视觉连通性生成虚假节点或边。

### 9.5 预期改动面

- 新网络页面、图谱组件和样式；
- 节点详情抽屉与选中对象联合类型；
- 导航入口；
- 网络 API 的分页或局部加载增强；
- E2E、无障碍、视觉和性能测试。

### 9.6 验收门

- [ ] 用户能够从图谱打开 Concept、Knowledge Point 和来源记录；
- [ ] 图中每条边均对应后端返回的真实确认事实；
- [ ] 起终点选择、路径高亮和无路径结果可重复验证；
- [ ] URL、刷新、返回键、抽屉和布局状态符合约定；
- [ ] 键盘和列表模式可完成核心浏览与路径操作；
- [ ] 目标规模下交互、内存和布局时间达到预先确定的预算；
- [ ] 2D 图谱验收完成后，V3 核心产品标准视为完成。

## 10. V3.4：3D 体验升级

### 10.1 目标

在 V3.3 的稳定网络 API 和交互合同上增加 3D 表现，不引入新的领域语义。

### 10.2 交付范围

- 抽取现有首页可复用的摄像机、WebGL2 检测、上下文恢复、LOD 和减少动态效果基础设施；
- 新建真实网络 3D 渲染层，不直接把当前 Tag 节点和装饰连线改名复用；
- 第一批只替换一个既有主舞台，默认优先评估首页；
- 搜索页继续保留稳定相关性结果，除非另一个独立里程碑明确批准替换；
- 复用 V3.3 的节点选择、URL、详情抽屉和路径合同；
- WebGL2 不可用或上下文不可恢复时自动回到 V3.3 功能视图。

### 10.3 决策门

- 首页与搜索舞台哪个先接入真实图谱；
- 3D 坐标是持久化、服务端生成还是客户端稳定计算；
- Concept 与 Knowledge Point 的默认展开层级；
- 目标节点、边数量和正式支持浏览器的性能预算；
- 3D 与 2D 是否共享布局快照。

### 10.4 明确不做

- 同一里程碑同时重写首页和搜索页；
- 用视觉距离代替关系类型；
- 因 3D 失败关闭网络查询、Concept 管理或路径探索；
- 引入图数据库来解决纯渲染问题。

### 10.5 验收门

- [ ] 3D 和 2D 展示相同的真实节点、边和选中对象；
- [ ] 3D 打开抽屉、聚焦或高亮路径不会重建领域关系；
- [ ] WebGL 上下文丢失后可以恢复或自动降级；
- [ ] 正式浏览器和目标规模达到帧率、内存和交互预算；
- [ ] 视觉回归覆盖两套主题、减少动态效果和 2D 降级；
- [ ] V3.4 不改变 V3.3 已验证的网络语义。

## 11. 每个里程碑的执行顺序

每个里程碑内部固定按照以下顺序推进：

1. 解决本阶段决策门，更新 CONTEXT、PRD 和必要 ADR；
2. 写出迁移、领域不变量和失败场景测试；
3. 添加增量数据库迁移并验证旧数据升级；
4. 实现领域/API 行为；
5. 同步升级导出恢复和兼容测试；
6. 实现客户端 API、页面与交互；
7. 补齐 E2E、无障碍、视觉与性能验证；
8. 对照本阶段验收门逐项关闭；
9. 更新本文进度后，才能进入下一阶段。

实现中不得为了后续里程碑预先加入未使用的表、字段、API 或抽象。只有当前阶段的测试和用户行为真正需要时才新增结构。

## 12. 跨阶段完成定义

任一里程碑只有同时满足以下条件才算完成：

- 范围内功能能够通过正式 UI 或明确 API 使用；
- 新领域词已经进入 CONTEXT，难以逆转的决定已经进入 ADR；
- 数据库迁移只做增量变更，并在现有 V2 数据上通过验证；
- 当前导出格式包含本阶段全部持久化领域事实；
- 全部承诺支持的旧导出格式仍可恢复；
- 新增状态、并发、迟到结果、撤销、归档和过期边界有自动测试；
- TypeScript 类型检查、Vitest、API、E2E 和相关视觉测试通过；
- 没有把下一阶段能力作为当前阶段完成的隐含前提；
- 本文的进度、遗留事项和下一阶段决策门已经更新。

## 13. 延后范围

下列能力不属于 V3.0–V3.4 的默认完成范围，除非先更新 PRD 和本文：

- Concept 别名、层级和合并；
- 用户自定义关系类型及关系类型管理器；
- Knowledge Point 跨分析版本自动身份映射；
- 无用户动作的持续后台聚类或自动归属；
- 自动创建、自动修复或自动删除正式图谱边；
- 图数据库、搜索集群或独立图计算服务；
- 基于图谱生成无来源的问答答案；
- 移动端专用图谱体验。
