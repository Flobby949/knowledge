# V2 → V3 晋级路线

> 状态：V3 路线已全部实现并验收 · 基线日期：2026-08-11 · 完成日期：2026-08-12

## 1. 文档目的

本文把 [PRD](../PRD.md) 中一次性描述的 V3 能力拆成可独立实现、验证和发布的阶段。后续实现默认按照本文顺序推进；如果范围、顺序或领域语义发生变化，必须先更新本文及相关领域文档，再修改代码。

本文只细化交付路线，不取代其他基线：

- [CONTEXT.md](../CONTEXT.md) 定义领域语言；
- [PRD.md](../PRD.md) 定义产品范围和最终完成标准；
- 已接受的 [ADR](./adr) 记录难以逆转的架构决定；
- 本文定义版本切分、依赖关系、阶段边界和验收门。

本文中的 `V2.1`、`V3.0` 至 `V3.4` 是产品能力里程碑，不要求与部署使用的 Git 发布标签一一对应。

## 2. 最终目标

完成本路线后，系统应具备以下能力：

1. 用户可以主动创建 Concept，并把多个知识点纳入 Concept；
2. AI 可以基于多个生效知识点提出 Concept Candidate，但不能自动创建正式 Concept；
3. 用户可以确认、修改或拒绝候选，所有决定均保留来源和历史；
4. Concept、知识点归属、知识点关系和 Concept 关系可以组成可查询的知识网络；
5. 用户可以查看真实图谱、选中节点、回到来源并探索可解释路径；
6. 所有新增领域事实都能完整导出和恢复，并从格式 4 起向后兼容已经发布的备份；
7. V1/V2 已有记录、历史版本、知识点、证据、标签和治理决定不被批量改写；
8. 首页以真实 3D 网络呈现同一组可核验节点和边，并能在渲染失败时保留状态回到功能性 2D 与键盘列表。

## 3. 全路线固定原则

### 3.1 人工确认边界

- AI 输出只能形成 Candidate 或 Suggestion；
- 只有用户明确确认后才能形成 Concept 或正式关系；
- Mode A 不适用于 Concept 和知识关系；
- 相似度、聚类结果和模型置信度都不能直接进入正式知识网络。

### 3.2 版本与溯源

- Concept Membership 初期绑定一个确切、不可变的 Knowledge Point；
- 重新整理产生新的 Knowledge Point 身份时，不自动迁移归属；
- 原端点不再生效、被排除或内容变化时，归属和关系保留历史并显示需要复核；
- 自动跨版本身份映射不属于本路线的核心范围。

### 3.3 增量数据模型

- V3 只新增结构，不批量改写 V1/V2 领域行；
- 现有 `knowledge_relations` 继续表达 Knowledge Point → Knowledge Point；
- Concept、Concept Membership 和 Concept Relation 使用独立结构；
- 知识网络通过只读聚合模型联合现有关系与新增结构，不先改造成通用多态边表；
- PostgreSQL 仍是唯一事实存储，在出现经过测量的性能瓶颈前不引入图数据库。

### 3.4 可移植性不延期

- 每个新增持久化领域对象必须在同一里程碑进入完整导出与恢复；
- 格式 4 是首个恢复兼容基线；每次格式升级都必须继续接受格式 4 及之后已经发布的格式；
- 格式 1–3 没有形成用户持有的历史备份，不纳入恢复兼容范围；
- 导出恢复、引用校验和迁移测试不是最后统一补做的收尾项。

### 3.5 先语义、后图形

- 先建立可测试的 Concept 和网络语义，再开发图谱；
- 先交付功能完整的 2D 图谱，再升级 3D 体验；
- 图谱只显示真实领域关系，装饰线不得伪装成知识边；
- 3D 渲染失败不能阻断 Concept、路径查询和来源核验。

## 4. 路线总览

| 里程碑 | 核心结果 | 相对规模 | 依赖 |
| --- | --- | --- | --- |
| V2.1 V2 收尾 | 验收 V2 完成标准，冻结导出兼容基线 | 小 | 当前 V2 |
| V3.0 Concept 核心 | 用户可以手动创建和维护 Concept 与归属 | 中 | V2.1 |
| V3.1 Concept Candidate | AI 候选和人工审查形成闭环 | 中高 | V3.0 |
| V3.2 知识网络语义 | 可查询节点、边、邻居和路径 | 高 | V3.0；可与 V3.1 部分并行 |
| V3.3 功能性图谱 | 独立 2D 知识网络工作台 | 高 | V3.1、V3.2 |
| V3.4 3D 体验升级 | 将真实网络接入一个既有主舞台 | 高（已实现） | V3.3 |

顺序如下：

```text
V2.1 → V3.0 → ┬→ V3.1 ─┐
               └→ V3.2 ─┴→ V3.3 → V3.4
```

V3.1 与 V3.2 只有在 V3.0 的数据库结构、API 合同和领域测试稳定后才可以并行。

## 5. V2.1：V2 收尾

### 5.1 目标

逐项验收 V2 完成标准，让 V2 成为能够安全承接后续格式升级和新增领域对象的稳定基线。本阶段没有 V3 用户功能。

### 5.2 交付范围

- 对照 PRD 16.2 审计标签治理、重复建议、关系建议与确认、覆盖分析和 V1 数据保持行为；
- 验证 V2 数据库迁移只新增结构，不批量改写 V1 领域行；
- 验证当前完整导出格式 4 包含全部 V2 领域事实，并能事务性恢复到空实例；
- 把格式 4 固定为首个恢复兼容基线，不为未形成用户备份的格式 1–3 增加适配器；
- 通过类型检查、领域与集成测试、端到端测试和双主题视觉回归。

### 5.3 导出兼容边界

- 恢复器只接受当前受支持格式，并继续执行严格结构、引用和空实例校验；
- 格式 4 以前的开发期格式不构成公开兼容承诺；
- 一旦后续格式正式发布，恢复器必须继续支持格式 4 及之后已经发布的格式；
- 当前导出格式升级时必须同步增加固定恢复样本和往返测试。

### 5.4 预期改动面

- 现有 `src/data-transfer-routes.ts` 已严格支持格式 4，无需修改生产代码；
- 复用现有迁移、V2 导出恢复、领域、集成、E2E 和视觉测试；
- 更新 PRD、路线文档和导出兼容 ADR；
- 不新增前端入口，不新增 Concept 表。

### 5.5 验收门

- [x] 当前格式 4 的有效备份能够事务性恢复到空实例；
- [x] 缺字段、额外字段、错误引用和损坏 ZIP 继续严格失败；
- [x] 全部 V2 领域事实经过当前格式导出恢复后不丢失；
- [x] V2 完成标准逐项有自动测试或明确验收证据；
- [x] 类型检查、Vitest、API/E2E 和双主题视觉测试通过。

## 6. V3.0：Concept 核心

### 6.1 目标

不依赖 AI 和图谱，让用户先能够建立、阅读和维护正式 Concept，验证最核心的长期聚合模型是否成立。

### 6.2 实施前领域决策门

以下问题已经在数据库迁移前确定，并由 PRD、CONTEXT 与 ADR-0031 固定：

- [x] Concept 名称和自足描述均为必填；名称使用 NFKC、Unicode 空白归一和拉丁字母大小写无关规则，在独立于 Tag 的 Concept 命名空间内唯一；
- [x] 名称与描述修改产生不可变 Concept Revision，Concept 稳定身份不变；
- [x] Concept 只支持可恢复归档，V3.0 不提供永久删除；
- [x] Membership 保持同一身份并记录加入、移除和恢复；端点失效后保留原引用、标记复核且不自动迁移；
- [x] V3.0 不新增 Concept Relation 或关系类型；Concept Relation 类型集合留到 V3.2 的关系决策门确定。

其余固定边界是：用户主动创建时至少聚合两个生效且未排除的知识点；后续成员不足不会自动删除或归档 Concept。

### 6.3 交付范围

- 新增 Concept 持久化结构；
- 新增 Concept Membership 持久化结构；
- 用户可以从多个当前生效且未排除的 Knowledge Point 创建 Concept；
- 用户可以修改 Concept 名称和描述；
- 用户可以增加、移除和恢复 Membership；
- 用户可以归档和恢复 Concept；
- Concept 详情展示成员知识点、实际来源记录、端点状态和归属来源；
- 新增 Concept 列表、详情和编辑 API；
- 新增独立 Concept 工作区，避免继续扩大现有 `insights-page.tsx` 单文件；
- 完整导出与恢复包含 Concept 和 Membership，并继续支持格式 4 及之后已经发布的格式。

### 6.4 固定领域行为

- Concept 不是 Tag，不进入标签词表，也不产生 Tag Assignment；
- Concept 是用户确认后的长期节点，用户手动创建即构成明确确认；
- Membership 是可撤销事实，移除不删除知识点或历史归属；
- Membership 绑定确切 Knowledge Point，不因重新整理自动改指向新知识点；
- Knowledge Point 不再生效时，历史 Membership 仍可查看，但不进入默认有效网络；
- 归档 Concept 不删除成员、来源或关系历史。

### 6.5 明确不做

- Concept Candidate；
- AI 自动发现或后台聚类；
- Concept Relation；
- 图谱和路径探索；
- Concept 别名、层级、合并；
- 自定义关系类型；
- 跨分析版本自动迁移 Membership。

### 6.6 预期改动面

- 1–2 个增量数据库迁移；
- 新 Concept 领域/API 模块及客户端 API 类型；
- 新 Concept 列表与详情页面；
- 导航增加可发现入口，但不替换首页或搜索；
- 导出恢复格式升级及格式 4 以后已发布格式的适配；
- 迁移、API、集成、E2E 和导出恢复测试。

### 6.7 验收门

- [x] 用户能够从至少两个有效知识点创建 Concept；
- [x] Concept 和 Membership 的创建、修改、撤销、归档与恢复均可追溯；
- [x] 重分析、排除知识点和归档记录不会静默改写 Membership；
- [x] Concept 永远不会混入 Tag 或 Tag Assignment；
- [x] V2 数据升级前后身份、内容和引用保持不变；
- [x] 当前格式 7 与已发布格式 4、5、6 均可恢复；
- [x] 核心领域、API、E2E 和恢复测试通过。

## 7. V3.1：Concept Candidate

### 7.1 目标

让系统在新知识生效后自动进行全局关联召回，由 AI 提出可审查的 Concept Candidate，并通过人工确认形成正式 Concept 和 Membership。

### 7.2 交付范围

- 新增 Concept Candidate 及其输入知识点快照；
- Candidate 保存建议名称、描述、成员、生成理由、模型信息和输入内容指纹；
- AI Analysis Revision 首次成为当前生效知识后，以其中的知识点为种子自动发起扫描；
- 用户可以一键为尚未覆盖的历史生效分析补做全量概念发现，不选择知识点且不直接创建 Concept；
- 从全局当前生效且未排除的知识点中召回关联输入，用户不选择扫描范围；
- “仅保存”只进入全局原文检索，不进入 Concept 召回；Mode A 自动采用后触发，Mode B 整份审查完成并生效后触发；
- 生成过程具有排队、运行、成功、失败和重试等可观察状态；
- 用户可以修改名称、描述和成员后确认，也可以拒绝或稍后处理；
- 确认操作在同一事务中创建 Concept、Membership 和确认记录；
- 同一输入及内容指纹已经确认或拒绝后，不重复提出等价候选；
- 输入知识点发生实质变化时，Candidate 显示过期并阻止直接确认；
- Candidate 和全部审查决定进入导出恢复。

### 7.3 自动召回边界

- 自动发现由新的生效分析事件触发，不在部署或定时任务中静默回填历史分析；用户可以显式执行幂等的全量概念发现来补齐尚未覆盖的当前生效分析；
- 全量发现复用持久化发现队列并按有界并发消费，已有自动扫描或待办视为已覆盖，不重复计算；
- 只召回全局当前生效、未排除且 Embedding 已就绪的 Knowledge Point，并记录完整快照；
- Embedding 只负责关联召回，文本模型负责给出候选内容和理由；
- 召回阈值不能直接创建 Concept，也不能替代用户确认。

V3.1 实施时以本次生效知识点为种子，按语义相似度补充召回，总输入固定为 1–12 个、最多一个候选；只有一个输入时直接记录无建议结果。候选任务超时按输入扩展字素数量在 5–10 分钟间分档，失败任务最多由用户显式重试一次。边界由召回器、生成器与公开 API 测试固定。

### 7.4 明确不做

- 自动确认 Candidate；
- 自动把新分析版本加入已有 Concept；
- Concept 合并、别名或层级；
- 图谱布局；
- 定时或持续执行的全库后台聚类。

### 7.5 预期改动面

- Candidate、输入快照和任务生命周期迁移；
- Concept 生成器、校验器、路由和任务恢复逻辑；
- Candidate 审查工作区；
- AI 任务观察入口；
- 导出恢复及兼容测试；
- 领域、集成、E2E 和超时/重试测试。

### 7.6 验收门

- [x] AI 只能创建 Candidate，不能直接写入 Concept；
- [x] Candidate 的每个成员都能回到确切 Knowledge Point 和原文证据；
- [x] 确认、修改后确认、拒绝和过期行为均有集成测试；
- [x] 迟到任务不会基于已变化的输入发布可确认 Candidate；
- [x] 等价的已处理输入不会反复推荐；
- [x] 任务失败不影响已有 Concept、记录和搜索；
- [x] Candidate 与决定可以完整导出恢复。

## 8. V3.2：知识网络语义与 API

### 8.1 目标

先建立与渲染器无关、可验证的知识网络读取模型，使节点、边、邻居和路径都拥有稳定语义。

### 8.2 网络读取模型

第一版网络包含：

- 节点：有效 Concept、当前生效且未排除的 Knowledge Point；
- 边：`concept_membership`，连接有效 Concept 与当前有效 Knowledge Point，按无向边遍历；
- 边：`knowledge_relation`，连接两个当前有效 Knowledge Point，只包含 V2 已确认且未撤销、输入仍有效的 Knowledge Relation；
- 边：`concept_relation`，连接两个有效 Concept，只包含 V3 已确认且未撤销、冻结 Revision 与 Membership 指纹仍有效的 Concept Relation。

默认网络和路径只使用当前有效且已确认的事实。历史端点、已撤销边和需要复核的边仍可在详情中查看，但不参与默认遍历。

### 8.3 交付范围

- 新增 Concept Relation 及必要的建议/确认结构；
- 修正 Record 永久删除与 Concept Membership 历史引用之间的级联边界；
- 保留现有 Knowledge Relation 表，不迁移成多态边；
- 提供 `GET /api/v1/network/subgraph` 与 `GET /api/v1/network/nodes/:typedKey/neighbors` 读取 Concept-first 子图或指定节点邻居；节点统一使用 `concept:<uuid>`、`knowledge_point:<uuid>` typed key；
- 提供 `GET /api/v1/network/path` 探索有边界路径；`from` 与 `to` 也使用 typed key；
- 节点返回当前内容及 Concept Revision 或 Knowledge Point 来源；边返回稳定 `edgeKey`、三类真实 `kind`、规范 source/target、关系类型、是否有向、描述和来源/确认记录；路径另返回有序节点、真实边及每一步的 `forward`、`reverse` 或 `undirected` 遍历方向；
- Concept 详情展示直接邻居和已确认关系；
- Concept Relation Suggestion 支持扫描、列表、修改后确认、拒绝，正式 Concept Relation 支持列表和撤销；
- 所有网络对象和确认记录进入格式 8 完整导出恢复，恢复器继续接受格式 4–7；
- 局部子图最多 300 个节点、600 条边、深度 2，并返回节点/边截断状态；路径最大深度 6、最多访问 1000 个节点并使用 2 秒数据库查询预算，超过预算返回明确错误。

### 8.4 关系决策门

以下问题已经在 Concept Relation 迁移前确定，并由 PRD、CONTEXT 与 ADR-0034 固定：

- [x] 第一版只允许 AI Suggestion 经用户人工确认形成正式 Concept Relation，不提供直接创建；
- [x] 完全复用 V2 六种预设类型；`SIMILAR`、`CONTRASTS`、`ANALOGY` 对称，`PREREQUISITE`、`EXTENDS`、`APPLIES` 有向；
- [x] 路径允许反向遍历，但每一步保留正式关系的规范 source、target 与本次遍历方向；
- [x] 同一对 Concept 可以同时存在不同类型的有效关系，同一规范端点、方向与类型最多一个有效关系；
- [x] Suggestion 冻结两端不可变 Concept Revision 与当时有效 Membership 集合的 SHA-256 指纹，不建立成员快照表；
- [x] 端点归档、当前 Revision 或有效 Membership 集合变化使正式边需要复核并退出默认网络，建议、确认、撤销和过期历史均不删除。

### 8.5 路径语义

- 路径是现有确认事实的遍历结果，不是 AI 推理链；
- 每一步必须引用一个真实 Membership、Knowledge Relation 或 Concept Relation；
- 反向遍历只改变该路径步骤的行进方向，不改写关系确认时的规范方向；
- 系统不得为了连通两个节点而生成不存在的中间关系；
- 找不到路径是有效结果，不降级为语义相似度解释；
- 第一版优先使用 PostgreSQL 查询或服务端有界遍历，不引入图数据库。

### 8.6 明确不做

- 图谱渲染；
- 自定义关系类型编辑器；
- Ontology；
- 自动修复或补全断开的路径；
- 基于图路径生成无来源的 AI 答案。

### 8.7 验收门

- [x] 网络 API 只返回有效、已确认的默认节点和边；
- [x] 任一节点和边都能回到来源与确认记录；
- [x] 邻居、方向、多关系、撤销、归档和过期行为有集成测试；
- [x] 路径结果逐边可核验，找不到路径时明确返回空结果；
- [x] 大输入受到边界和超时保护；
- [x] 不需要 Neo4j 等新增基础设施即可通过目标规模测试；
- [x] 全部网络对象可以完整导出恢复。

## 9. V3.3：功能性知识图谱

### 9.1 目标

在不依赖 3D 的前提下完成真实知识网络的浏览、选中、核验和路径探索，达到 PRD 的核心 V3 完成标准。

### 9.2 交付范围

- 新增独立 `/network` 工作区；
- 初始视图以 Concept 为主要节点，Knowledge Point 按选择或局部展开加载；
- 只绘制网络 API 返回的真实边；
- 支持节点搜索、类型筛选、关系筛选、聚焦和重置视图；
- 支持选择起点和终点并高亮一条可解释路径；
- 节点选择写入 URL，刷新、浏览器返回和前进保持预期状态；
- 右侧推挤式详情抽屉支持 Concept 和 Knowledge Point；
- 打开抽屉只调整视口，不重新计算稳定布局；
- 提供键盘可操作的等价节点/关系列表；
- 遵循减少动态效果偏好，渲染失败时保留功能性列表视图。

### 9.3 布局原则

- 布局只表达真实网络结构，不使用无语义随机邻接；
- 同一网络快照在多次访问中保持稳定，不因抽屉开合重排；
- 局部扩展不得让已显示节点发生无法追踪的大幅跳动；
- 颜色不能成为区分节点类型、关系类型或状态的唯一方式；
- 装饰元素必须与真实关系边有可感知差异，默认优先不画装饰线。

### 9.4 固定实现合同

- `/network` 是独立工作区；V3.3 不替换首页或搜索结果页；
- 初始图只加载有效 Concept，选中、节点搜索、路径或局部展开时才补入相关 Knowledge Point；
- 客户端以排序后的 typed node key 与真实 edge key 计算版本化、确定性的 2D 布局快照；筛选、路径高亮和 480px 推挤式抽屉不重算布局，局部展开冻结全部旧坐标；
- URL 使用 `node`、`from`、`to`、提交后的 `q`、重复 `type`、重复 `relation` 和 `view=graph|list`；坐标、缩放和摄像机状态不写入 URL；
- 路径只使用服务端返回的有序真实边；客户端不得自行推断路径或把反向遍历改写为反向事实；
- SVG 与键盘等价列表共享搜索、筛选、选择、路径和详情状态；SVG 或布局 Worker 失败时自动保留状态并切到列表；
- V3.3 不引入 React Flow、Cytoscape、D3 force、图数据库或新的持久化布局表。

性能验收固定为 300 个节点、600 条真实边：预热后的确定性初始布局 p95 不超过 250ms，局部展开不超过 150ms，图幅首次可交互不超过 1.5s，指针和键盘反馈不超过 100ms，浏览器页面堆增量不超过 50MiB；超限必须由现有 API 截断合同明确表达，不静默丢边。浏览器规模验收使用路由 fixture 合成同样数量的有效节点和真实边，不放宽线上 API 上限。

### 9.5 明确不做

- 替换现有首页；
- 替换搜索结果主舞台；
- 3D 自由漫游；
- Concept 别名、层级或自定义关系类型；
- 为视觉连通性生成虚假节点或边。

### 9.6 预期改动面

- 新网络页面、图谱组件和样式；
- 节点详情抽屉与选中对象联合类型；
- 导航入口；
- 网络 API 的分页或局部加载增强；
- E2E、无障碍、视觉和性能测试。

### 9.7 验收门

- [x] 用户能够从图谱打开 Concept、Knowledge Point 和来源记录；
- [x] 图中每条边均对应后端返回的真实确认事实；
- [x] 起终点选择、路径高亮和无路径结果可重复验证；
- [x] URL、刷新、返回键、抽屉和布局状态符合约定；
- [x] 键盘和列表模式可完成核心浏览与路径操作；
- [x] 目标规模下交互、内存和布局时间达到预先确定的预算；
- [x] 2D 图谱验收完成后，V3 核心产品标准视为完成。

## 10. V3.4：3D 体验升级

### 10.1 目标

在 V3.3 的稳定网络 API 和交互合同上增加 3D 表现，不引入新的领域语义。

### 10.2 交付范围

- [x] 抽取路由感知的共享网络工作区控制器，统一管理 Concept-first 装载、root/path 合并、节点搜索、确定性 Worker 布局、URL、筛选、抽屉历史、可见节点/边和保存后刷新；
- [x] 新建真实网络 3D 模型与渲染层，复用 V3.3 x/y 并按 typed node key 派生稳定浅层 z，不直接把旧 Tag 节点或装饰线改名复用；
- [x] 第一批只替换首页主舞台，独立 `/network` 保持正典 2D 工作区与降级视图；
- [x] 搜索页继续保留稳定相关性结果，首页底部继续提供独立的 Tag 定位／记录搜索；
- [x] 首页复用 V3.3 的节点选择、URL、重复筛选、480px 详情抽屉、浏览历史、服务端路径和键盘列表合同；
- [x] WebGL2、初始化、帧渲染或上下文失败时保留网络状态回到 2D，2D 再失败进入列表；减少动态效果使用按需单帧渲染。

### 10.3 已固定决策

完整边界与取舍见 [ADR-0036：首页真实 3D 网络复用功能性网络合同](./adr/0036-home-3d-reuses-network-workspace-contract.md)。

- 首页是第一个真实 3D 知识网络主舞台；搜索页继续使用稳定相关性结果，`/network` 保持正典 2D 工作区与降级视图；
- 3D 与 2D 共享 V3.3 版本化、确定性的客户端布局快照。3D 原样使用 x/y，只按 typed node key 派生稳定、浅层且有界的 z；z 不持久化、不进入 API 或 URL，也不表达关系类型、强弱、相似度、层级或中心性；
- 初始舞台只加载当前有效 Concept，选择、节点搜索、路径或局部展开需要时才加入 Knowledge Point；局部展开冻结已有节点的 x/y/z；
- 3D 复用 V3.3 的 typed node key、三类真实边、URL、节点选择、路径、480px 详情抽屉和键盘等价列表；首页底部 Tag／记录搜索和新建记录入口继续保留，Tag 不进入真实知识网络；
- WebGL2 不可用、初始化或帧渲染异常、上下文不可恢复丢失时，在保留查询、URL、选择、路径和抽屉状态的前提下降级到 V3.3 2D；2D 渲染再失败时进入同状态的列表。减少动态效果偏好下不得运行持续 `requestAnimationFrame` 循环；
- 首页真实网络不得复用旧 Tag 场的随机位置、虚假装饰连线、按关联记录数缩放或 `USER_APPROVED`／`CANDIDATE` 状态语义。

正式支持当前稳定版 Chrome 与 Edge 桌面端，并在 1280×800 与 1600×1000、设备像素比不超过 2 的环境验收。合成的 500 个节点／1000 条真实边只用于 3D 渲染压力，不改变线上网络 API 的 300 节点／600 边上限；压力场景的交互帧时间 p95 不超过 20ms、任一单帧不超过 50ms，确定性布局不超过 250ms，首次可交互不超过 1.5s，页面堆增量不超过 64MB。减少动态效果下持续 RAF 数量必须为零。

### 10.4 明确不做

- 同一里程碑同时重写首页和搜索页；
- 用视觉距离代替关系类型；
- 因 3D 失败关闭网络查询、Concept 管理或路径探索；
- 引入图数据库来解决纯渲染问题。

### 10.5 验收门

- 当前状态：已完成；自动化、视觉、性能与本地 Docker 部署验收均已通过。
- [x] 3D 和 2D 展示相同的真实节点、边和选中对象；
- [x] 3D 打开抽屉、聚焦或高亮路径不会重建领域关系；
- [x] WebGL 上下文丢失后可以恢复或自动降级；
- [x] 正式浏览器和目标规模达到帧率、内存和交互预算；

- [x] V3.4 不改变 V3.3 已验证的网络语义。

### 10.6 实现落点与最终验收

实现落点已经固定为：共享网络工作区控制器；独立的 3D 数据模型与 WebGL 渲染器；首页对真实网络搜索、筛选、选择、路径、详情、新建后刷新和 `3D → 2D → list` 的集成；`/network` 继续使用同一控制器维持 V3.3 行为。首页 surface brief 与 ADR-0036 共同约束“只有 Concept、Knowledge Point 与三类真实边进入网络，Tag 只保留独立搜索入口”。

## 11. 每个里程碑的执行顺序

每个里程碑内部固定按照以下顺序推进：

1. 解决本阶段决策门，更新 CONTEXT、PRD 和必要 ADR；
2. 写出迁移、领域不变量和失败场景测试；
3. 添加增量数据库迁移并验证旧数据升级；
4. 实现领域/API 行为；
5. 同步升级导出恢复和兼容测试；
6. 实现客户端 API、页面与交互；
7. 补齐 E2E、无障碍、视觉与性能验证；
8. 对照本阶段验收门逐项关闭；
9. 更新本文进度后，才能进入下一阶段。

实现中不得为了后续里程碑预先加入未使用的表、字段、API 或抽象。只有当前阶段的测试和用户行为真正需要时才新增结构。

## 12. 跨阶段完成定义

任一里程碑只有同时满足以下条件才算完成：

- 范围内功能能够通过正式 UI 或明确 API 使用；
- 新领域词已经进入 CONTEXT，难以逆转的决定已经进入 ADR；
- 数据库迁移只做增量变更，并在现有 V2 数据上通过验证；
- 当前导出格式包含本阶段全部持久化领域事实；
- 全部承诺支持的旧导出格式仍可恢复；
- 新增状态、并发、迟到结果、撤销、归档和过期边界有自动测试；
- TypeScript 类型检查、Vitest、API、E2E 和相关视觉测试通过；
- 没有把下一阶段能力作为当前阶段完成的隐含前提；
- 本文的进度、遗留事项和下一阶段决策门已经更新。
