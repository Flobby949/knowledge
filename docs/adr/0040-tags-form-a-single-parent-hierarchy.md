# 标签使用单父层级并保持名称全局唯一

标签支持多级组织：每个 `USER_APPROVED`、未归档且不是有效合并来源的 Tag 可以拥有至多一个同样满足条件的上级 Tag，形成深度不超过 5 级的单父树；没有上级的 Tag 位于顶层。层级保存为 Tag 上可变的 `parent_tag_id`，用户可以随时移动；标签路径只由上级链派生用于展示，不写入名称。`normalized_name` 继续在整个实例内唯一，同名标签不能分属不同分支，因此按名称选择、AI 候选复用、别名解析和恢复校验仍然依赖“一个名称对应一个标签”。名称中的 `/` 等标点照常保留，不解析为层级分隔符。

按标签筛选记录时，所选 Tag 先解析到主标签，再包含它的全部下级 Tag：记录的有效标签集合只要命中所选子树中的任一 Tag 即通过筛选，多个所选标签之间仍为 OR。标签的关联记录数默认按包含下级的去重有效记录计算，与点击筛选得到的结果一致；只计直接关联的数量继续保留，用于标签治理。首页神经标签场继续平铺展示全部现存 Tag，节点尺寸按包含下级的数量计算，聚焦 HUD 与标签定位显示完整路径；空间位置、色相和装饰线仍不表达层级、分类或关系。

AI 候选标签不参与层级。候选始终位于顶层，AI 不决定标签放在哪里；用户认可候选时可以同时选择上级。为避免层级与合并、归档互相缠绕，有下级的 Tag 不能归档，也不能作为合并来源；Tag 被归档或成为合并来源时退出层级并回到顶层，恢复或撤销合并后仍位于顶层，由用户重新移动。移动不得形成环，也不得让任何下级超过深度上限。

完整导出格式升级为 9，在 Tag 上保存 `parent_tag_id`；格式 4–8 中的 Tag 恢复后均位于顶层。恢复前整包校验上级存在、无环、深度不超限，以及候选、归档标签和有效合并来源不处于层级中。

未采用的方案：把路径写进名称会让改动上级变成批量改名，并把 `CI/CD`、`TCP/IP` 等既有名称误拆成两级；同一上级下唯一会使 AI 输出的同名候选无法确定分支，别名、合并与恢复的唯一性也需要重写；多上级层级会让筛选和计数语义难以解释；由 AI 自动分类违背候选必须由用户认可的边界。标签层级只表达用户自己的导航与分类归属，不是 Concept 层级，也不进入知识网络。
